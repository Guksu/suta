# 요청한 디테일을 그대로 만드는가 — 요구 충족률 진단과 측정 설계

| 항목 | 내용 |
|------|------|
| 날짜 | 2026-11-26 |
| 계기 | 사용자 목표 "고객이 원하는 UI를 만들어 주는 구독형 제품", 그 방향 중 하나인 "유저가 원하는 디테일까지 구현 가능할 정도의 구현력". 지금 벤치마크는 자주 비기고, 요청한 것을 얼마나 지켰는지 직접 세는 지표가 없다 |
| 반영 | 없음. 스킬(`skills/`)과 기존 스크립트는 고치지 않았다. 새로 만든 것은 이 문서와 요청문·요구 목록 초안(`evals/benchmark/fidelity/`)뿐이다 |
| 실행 | 없음. claude CLI를 부르는 벤치마크(`run.mjs`·`judge.mjs`)는 돌리지 않았다 |

이 문서에서 쓰는 말이다.

- **요구 충족률(fidelity)**: 요청문에 적힌 요구를 낱개로 나눴을 때, 만든 화면이 지킨 요구의 비율이다.
- **낱개 요구**: 한 번에 하나만 확인하는 요구다. 예: "카드 모서리 12px", "'담기'를 누르면 숫자가 1 오른다".
- **계산된 스타일**: 브라우저가 CSS를 모두 적용한 뒤의 실제 값이다(`getComputedStyle`).
- **회귀**: 수정 요청 뒤에, 요청하지 않은 곳이 바뀌거나 전에 지키던 요구가 깨지는 것이다.
- **판단 불가**: 남은 자료로는 지켰는지 어겼는지 가릴 수 없는 것이다.

## 1. 한눈에

- **지난 실행의 생성물은 저장소에 없다.** `index.html`·캡처·대화 기록(`stream.jsonl`)은 저장소 밖 작업 폴더에 있었고 남지 않았다. 남은 것은 요청문 44개, 결과 JSON 24개(실행별 렌더 지표와 판정 이유 644개), 연구·작업 기록이다. 이 진단은 판정 이유와 기록으로 한 것이다.
- **지난 요청은 짧고, 값을 정하지 않았다.** 요청문 44개의 길이는 79~222자(중앙값 118자)다. 수치(px)·색(hex)·시간(ms)을 정한 요청은 없다. 그래서 "명시한 요구가 suta 기본값보다 우선한다"(`SKILL.md` 우선순위 1)는 한 번도 시험된 적이 없다.
- **지금 판정은 요청 충족을 가르지 못한다.** 항목별 판정 111번에서 "요청 충족" 항목은 95번(86%)이 비김이었다. 요청이 짧아 두 화면 모두 보이는 항목은 다 갖췄기 때문이다.
- **상태·상호작용 요구는 한 번도 확인되지 않았다.** 44개 요청 중 9개가 상태나 상호작용을 요구했다(오류 상태, 결과 없음, 시트·토스트, 확인 창, 필터 적용 뒤 개수 등). 판정은 정지 캡처만 보므로 19번 "보이지 않는다·확인할 수 없다"고 적었다.
- **근거로 가린 어김 유형 상위 셋**(suta 쪽 실행 수, 2절).
  1. 요청한 항목이 빠지거나 일부만 있음 — 6실행
  2. 요청한 값이 좁은 화면·첫 화면에서 보이지 않거나 잘림 — 6실행
  3. 요청에 없는 요소를 더함 — 6실행
  - 바로 뒤가 필수 표시를 요청대로 보이지 않음(5실행), 요청한 값끼리 맞지 않는 견본 데이터(5실행)다.
- **측정 설계**(4·5절): 요청마다 낱개 요구를 JSON으로 두고, Playwright로 계산된 스타일·요소·문구·상호작용 뒤 상태·애니메이션 시간을 확인한다. 대상은 선택자(selector, CSS로 요소를 고르는 식) 대신 역할·접근 이름과 요청문의 데이터 글자로 찾는다. 수정 요청 두 번에서 회귀를 잰다.
- **요청문 6개 초안**(3절): 앱 3·웹 3, 요구 114개(요청마다 18~20개), 그중 12개는 suta 기본값과 일부러 부딪친다.
- **실행 수와 비용**(7절): 요청 6 × 조건 2 × 반복 3 = 첫 요청 36번, 수정 요청 72번. 어림 비용은 약 120달러(90~155달러)다.

## 2. 지난 실행 다시 보기

### 2.1 남은 자료와 방법

| 자료 | 있는가 | 쓴 곳 |
|---|---|---|
| 요청문 44개(`evals/benchmark/*-prompts.json`) | 있다 | 낱개 요구로 나눔 |
| 생성된 `index.html`, 캡처(`shot-390.png`·`shot-1280.png`), 대화 기록 | 없다 | — |
| 결과 JSON 24개의 실행별 렌더 지표 | 있다 | 잘림·넘침 같은 마감 결함 확인 |
| 하나를 고르는 판정의 이유(결과 JSON의 `judge`·`judgeAlt`) | 있다 | 요구별 근거 |
| 항목별 판정(`*-rubric*.json`)의 항목 선택·이유·요청 밖 요소 | 있다 | 요청 충족 항목의 분포 |

- 판정 이유 644개를 모았다. 이유는 A·B로 적혀 있다. 판정 순서(`suta-first`·`base-first`)로 어느 쪽이 suta인지 되돌렸다.
- 빠짐·잘림·모순·안 보임을 뜻하는 낱말이 든 이유 352개를 한 개씩 읽었다.
- 판정 이유가 suta 쪽 화면에서 요청한 항목을 짚었으면 그 실행의 그 요구를 "어김"으로 셌다. 두 판정 모델이 같은 실행을 짚으면 한 번으로 셌다.

- `depth-*`·`hierarchy-*` 파일의 `baseline`은 suta 0.17이다. 이 문서에서는 두 쪽을 모두 "suta 조건"으로 본다.

### 2.2 요청별 표

구체적 요구가 있고 근거가 남은 요청만 적었다. 칸은 suta 조건의 실행 수다.

- "다 갖췄다고 적힘": 항목별 판정이 "두 화면 모두 요청 항목을 빠짐없이 담았다"처럼 적은 실행이다. 하나를 고르는 판정만 있는 요청은 판정이 낱개로 적지 않아 "—"다.

### 2.3 어김의 유형

| 판단 불가 — 상태·상호작용 | 18실행 이상 | 오류 상태, 결과 없음, 시트·토스트·끌어내리기, 확인 창, 필터 적용 뒤 개수 |

- 판단 불가가 가장 크다. 상태·상호작용 요구는 지금 측정에서 한 번도 확인된 적이 없다.
- 사진 자리를 회색 칸으로 비운 것(0.6 메뉴 상세·검색 결과, 0.14 앱 화면 판정 9번)은 어김으로 세지 않았다. 요청문 꼬리말이 이미지 파일을 막아 "사진"을 문자 그대로 지킬 수 없었다. 요청과 측정 조건이 부딪친 경우다. 새 요청문은 "사진 자리"라고 쓴다.
- C는 반대 방향의 어김이다. 요청하지 않은 것을 더하지 않는 것도 "말한 그대로"에 든다. 다만 판정자가 적은 "요청 밖 요소"는 판정 한 번에 평균 6개가 넘는다(suta 쪽 704개 / 판정 111번). 뒤로 가기·상단 메뉴·글자 수 같은 화면의 틀과 보이는 방식까지 적기 때문이다. 이 목록으로는 C를 셀 수 없다. 새 요구 목록은 "하지 말 것"을 요구로 적어 기계로 본다(예: E09 "카드로 감싸지 마").

### 2.4 측정 자체의 빈틈

- 정지 캡처는 처음 상태만 보여 준다. 상태·상호작용 요구는 판정이 볼 수 없다.
- 모바일 캡처는 2,400px에서 자른다. 그 아래에 있는 요청 항목은 판정에게 "없는 것"이다(재고 관리 0.19 3번째의 최근 내역이 의심된다).
- 고정 요소를 옮겨 찍는 방식에 결함이 있던 동안의 판정은 요청 항목을 "안 보인다"고 잘못 적었다(숙소 등록, 판매글 쓰기 — `docs/benchmark.md`에 기록).
- 항목별 판정의 "요청 충족"은 비김이 86%다. 짧은 요청에서는 이 항목이 아무것도 가르지 않는다.

## 4. 측정 설계 — 요구 충족률

### 4.1 흐름

1. `run.mjs`로 요청문 세트를 돌린다(바꾸지 않아도 된다. `--prompts evals/benchmark/fidelity/app-prompts.json`).
2. 새 스크립트 `scripts/benchmark/fidelity.mjs`(설계만)가 실행 폴더마다 `index.html`을 Chromium으로 연다. `requirements.json`의 요구마다 확인한다.
3. 요구 하나의 결과는 네 가지 중 하나다.
   - 지킴(met)
   - 어김(violated)
   - 찾지 못함(not-found): 대상 요소를 찾지 못했다. 어김과 따로 센다(4.3절).
   - 판정 필요(needs-judge): `type: judge`이거나 기계 확인이 약한 요구다.
4. 실행별 `fidelity.json`을 남기고, `report.mjs` 옆의 집계가 조건별 충족률을 낸다.

### 4.2 JSON 스키마

요구 하나는 이렇게 생겼다(전부는 `requirements.json`).

```json
{ "id": "R09", "kind": "수치", "text": "카드 사이 가로·세로 12px",
  "check": { "type": "spacing", "viewport": 390,
    "target": { "unit": ["소금빵", "우유식빵", "크루아상", "딸기 생크림 케이크", "바닐라 라떼", "앙버터"] },
    "expect": { "row": { "px": 12 }, "column": { "px": 12 } } } }
```

| 필드 | 뜻 |
|---|---|
| `kind` | 수치·색·상태·상호작용·모션·반응형·문구·접근성·구성·데이터 — 집계를 나누는 축 |
| `conflict` | suta 기본값·검사 규칙과 부딪치는 요구. `rule`(규칙 이름), `class`(취향·사용 문제), `expected`(무엇이 지킴인가) |
| `check.type` | 아래 표 |
| `check.viewport` | 390·320·1280·1440. 앱은 390(과 320), 웹은 1280·1440과 390 |
| `check.state` | `loading`·`empty`·`error` — 주소에 `?state=`를 붙여 연다 |
| `check.steps` | 확인 전에 할 조작. `click`·`longPress(ms)`·`drag(dx, dy)`·`scroll(y)`·`type(text)`·`press(key)`·`hover`·`tab`·`focus`·`wait(ms)` |
| `check.then` | 조작을 한 번 더 한 뒤의 기대값(스크롤 전후, 정렬 두 번 등) |
| `check.expect` | `px`(허용 오차 기본 1px)·`color`(hex, 색 거리 허용 2 — RGB 각 채널 차이의 합)·`equals`·`matches`(정규식)·`min`·`max`·`count` 등 |
| `report.mustMention` | 보고문(마지막 응답)에 있어야 할 말. 사용 문제를 요구대로 만든 경우에만 쓴다 |

| `check.type` | 무엇을 보나 | Playwright에서 |
|---|---|---|
| `style` | 대상의 계산된 스타일 | `getComputedStyle`. 그림자·그라데이션은 문자열을 쪼개 값으로 비교 |
| `spacing`·`columns` | 되풀이 단위 사이 간격, 열 수 | 상자 좌표(`getBoundingClientRect`)의 간격·서로 다른 x 위치 수 |
| `exists`·`count`·`text` | 요소가 보이는가, 몇 개인가, 문구 | 접근성 트리의 역할·이름, 보이는 글자 |
| `attr` | 상태 속성 | `aria-selected`·`aria-pressed`·`aria-checked`·`aria-expanded`·`aria-sort`·`disabled`, 입력값 |
| `order` | 순서·같은 줄·가로 넘김 | 상자 좌표, `scrollWidth > clientWidth` |
| `interaction` | 조작 뒤 상태 | `steps`를 한 뒤 위의 검사 |
| `timing` | 나타났다 사라지는 시간 | 조작 시각부터 보임·사라짐을 50ms 간격으로 확인 |
| `motion` | 애니메이션 시간·속성·방향 | 조작 직후 `document.getAnimations()`의 `duration`·대상 속성. JS로 움직이면 `requestAnimationFrame`마다 계산된 `transform`을 1초 동안 모아 시작·끝 시각을 구함 |
| `focus` | 포커스 이동·복귀 | `document.activeElement`의 역할·이름 |
| `reducedMotion` | 동작 줄이기 | `browser.newContext({ reducedMotion: 'reduce' })`로 같은 조작 뒤 애니메이션 목록 |
| `copyTone` | 말투 | 보이는 문장의 끝맺음을 해요체·합쇼체로 셈(식물 이름·날짜 같은 데이터는 뺌) |
| `covered` | 하단 고정 막대가 마지막 요소를 가리는가 | 지금 `measure.mjs`의 `coveredByFixedBar`와 같은 방식 |
| `size` | 누르는 영역 | 지금 `measure.mjs`의 터치 영역 검사와 같은 방식 |
| `judge` | 기계로 못 보는 요구 | 캡처 + 물음을 판정 모델에 준다 |

- 114개 중 기계로 확인하는 것은 113개다. 순수 판정(`judge`)은 `I06`(고객 이름이 실존 회사인가) 하나다.
- 기계 확인이 약한 것이 넷 있다. `E16`(당기면 새로고침 표시 — 새로 보인 요소가 있는지만 안다), `P01`·`F02`(말투 — 끝맺음 규칙으로 어림), `P06`의 보고문(낱말 찾기). 이 넷은 첫 회차에 사람이 결과를 확인해 규칙을 다듬는다.

### 4.3 생성물마다 다른 선택자 — 요소를 찾는 법

같은 요청이라도 실행마다 클래스 이름과 구조가 다르다. CSS 선택자를 요구에 적을 수 없다. 대상은 다음 순서로 찾는다.

1. **역할과 접근 이름.** "담기 버튼"은 `getByRole('button', { name: '담기' })`. 스크린 리더가 쓰는 이름이라 접근성을 지킨 화면일수록 잘 찾힌다.
2. **요청문의 데이터 글자(앵커).** "메뉴 카드"는 요청문에 준 메뉴 이름 여섯 개로 찾는다. 글자마다 조상을 올라가며, 형제 중에 다른 앵커를 품은 요소가 있는 가장 낮은 조상을 "되풀이 단위"로 잡는다. 카드·행이 이렇게 찾아진다. `unit`과 `inner`(단위 안의 요소, 예: 가격 글자)가 이 방식이다.
3. **관계.** "장바구니 아이콘 위 숫자"는 장바구니 버튼 상자와 겹치거나 가장 가까운, 숫자만 든 요소다(`near`). "맨 위 머리"는 화면 위에 붙은 `fixed`·`sticky` 요소다(`pinned`).
4. **찾지 못함.** 위 셋으로 못 찾으면 "찾지 못함"이다. 어김으로 세지 않고 따로 센다.

찾지 못함은 두 가지일 수 있다. 화면이 정말 요구를 어겼거나(버튼이 `div`라 역할이 없다), 찾는 규칙이 모자란 것이다. 첫 회차에서 찾지 못함을 모두 사람이 열어 보고 규칙을 고친다. 찾지 못함이 5% 아래로 내려가면 측정을 믿고 쓴다. 충족률은 두 가지로 낸다.

- 엄격: 지킴 ÷ (지킴 + 어김 + 찾지 못함)
- 너그러움: 지킴 ÷ (지킴 + 어김)

#### 요청문에 data 속성을 넣을까

요청문에 "요소마다 `data-req="R09"`를 붙여 줘"를 넣으면 찾기가 확실해진다. 본 측정에는 넣지 않는다.

| | 넣을 때 | 넣지 않을 때 |
|---|---|---|
| 찾기 | 확실하다. 찾지 못함이 거의 0 | 역할·앵커 규칙에 기댄다. 찾지 못함이 생긴다 |
| 요청의 자연스러움 | 실제 고객은 이렇게 쓰지 않는다 | 실제 요청과 같다 |
| 모델의 행동 | 요구 번호가 붙은 확인 목록을 받는 셈이다. 요구를 낱개로 풀게 되어 충족률이 오를 수 있다 | 모델이 스스로 낱개로 풀어야 한다 — 재려는 능력 그대로 |
| 부작용 | 번호를 엉뚱한 요소에 붙이면 그것도 어김인지 애매하다 | — |

- 대신 data 속성판을 **처치 조건**으로 쓸 수 있다. 같은 요청에 요구 번호를 붙인 판과 안 붙인 판을 비교하면 "요청을 낱개로 풀지 않음"(6절 가설 1)을 바로 시험한다. 본 측정 뒤 선택 실험으로 둔다.

### 4.4 순수 로직의 경계 — `scripts/lib/fidelity.ts`(TDD로 먼저 테스트)

브라우저 쪽은 관찰값(상자 좌표·계산된 스타일·속성·시각)만 모은다. 판정은 아래 순수 함수가 한다. `clipCheck.ts`와 같은 나눔이다. 테스트는 `demo/src/tests/`에 둔다.

| 함수 | 입력 → 출력 | 테스트할 것 |
|---|---|---|
| `parseSpec({ json })` | 요구 목록 → 검증된 목록 + 오류 | 없는 type, id 중복, revision이 없는 요구를 가리킴 |
| `parsePx({ value })`, `parseColor({ value })` | `"12px"`·`"rgb(…)"`·`"#C2410C"`·`oklch()` → 수·RGBA | 단위, 알파, 대소문자 |
| `compareExpect({ expect, actual })` | 기대값과 관찰값 → 지킴·어김 + 차이 설명 | 허용 오차 경계, 색 거리, 정규식, 범위 |
| `parseShadow`·`parseGradient` | 계산된 `box-shadow`·`background-image` 문자열 → 층·멈춤 색 목록 | 여러 층, `inset`, 색이 앞에 오는 형식 |
| `findRepeatUnit({ anchors, tree })` | 앵커 글자 + 조상 사슬 → 되풀이 단위 | 앵커 하나가 두 번 나옴, 단위가 `li`가 아닌 `div`, 앵커가 버튼 안 |
| `columnsOf({ boxes })`, `gapsOf({ boxes })` | 상자 좌표 → 열 수, 가로·세로 간격 | 마지막 줄이 덜 참, 하위 픽셀 반올림 |
| `animationVerdict({ samples, expect })` | 애니메이션 목록이나 시각별 값 → 시간·속성·방향 판정 | 지연(delay) 포함, `transform`과 `top`이 섞임, 움직임 없음 |
| `visibilityWindow({ samples })` | 시각별 보임 여부 → 나타난 시각·사라진 시각 | 깜빡임, 끝까지 안 사라짐 |
| `copyToneOf({ sentences, ignore })` | 보이는 문장 → 해요체·합쇼체·기타 개수 | "~습니다"와 "~어요"가 섞임, 데이터 글자 제외 |
| `verdict({ requirement, observation })` | 요구 + 관찰 → 지킴·어김·찾지 못함·판정 필요 | 대상 없음, 조작 실패, `then` 단계 |
| `summarizeFidelity({ results })` | 실행별 결과 → 조건별 충족률(엄격·너그러움), 종류별, 부딪침 여부별, 순서 3분위별 | 찾지 못함 처리, 빈 실행 |

### 4.5 집계

| 지표 | 계산 | 무엇을 보려고 |
|---|---|---|
| 요구 충족률(엄격·너그러움) | 4.3절 | 전체 비교 |
| 종류별 충족률 | `kind`별 | 상태·상호작용이 약한가 |
| 부딪치는 요구의 충족률 | `conflict`가 있는 12개만 | suta 기본값이 요청을 덮는가(가설 2). 일반 조건과의 차이가 핵심 |
| 위치별 충족률 | 요구 순서를 셋으로 나눔 | 긴 요청의 뒷부분을 놓치는가(가설 5) |
| 사용 문제 요구의 처리 | `P06` 화면 값 + 보고문 | 따르고 보고하는가 |
| 찾지 못함 비율 | 찾지 못함 ÷ 요구 | 측정을 믿을 수 있는가 |

- 기존 렌더 지표(`measure.mjs`)와 판정은 그대로 함께 돌린다. 충족률이 오를 때 결함 지표가 나빠지는지 같이 본다.

## 5. 수정 요청 흐름 — 회귀 재기

### 5.1 흐름

1. 첫 요청을 끝낸 작업 폴더를 `r1/`로 복사해 둔다.
2. 같은 세션을 이어서 수정 요청 V1을 준다. 지금 `run.mjs`는 `--no-session-persistence`라 이을 수 없다. 이 모드에서만 세션을 남기고, 첫 실행 기록의 `session_id`로 `--resume`한다(CLI 옵션은 실행 전에 `claude --help`로 확인한다). 결과를 `r2/`로 복사한다.
3. V2를 이어서 주고 `r3/`로 복사한다. 실제 고객처럼 차례로 고친다. V2의 기준은 `r2/`다.
4. 스냅숏마다 4절의 요구 검사를 모두 다시 돌린다.

### 5.2 지표

| 지표 | 계산 | 뜻 |
|---|---|---|
| 수정 반영 | 수정 요청의 `changes`·`adds`의 새 기대값이 지켜졌는가 | 요청한 곳이 바뀌었나 |
| 요구 회귀 | 수정이 건드리지 않은 요구 중, 앞 스냅숏에서 지킴이었는데 지금 어김인 수 | 가장 중요한 지표. 고객이 "다른 데는 왜 바뀌었어요?"라고 묻는 경우 |
| 범위 밖 스타일 변경 | 앞뒤 스냅숏에서 요소를 짝지은 뒤, 수정 범위(`scope.targets`) 밖 요소의 계산된 스타일이 바뀐 수 | 요구 목록에 없는 곳의 변화 |
| 범위 밖 화면 변경 면적 | 범위 밖 요소마다 앞뒤 요소 캡처를 비교해 달라진 픽셀 비율 | 스타일 이름으로 안 잡히는 변화(그림 속 SVG 등) |
| 파일 변경량(설명용) | `index.html` 줄 단위 차이 | 고칠 때 파일을 다시 썼는가 |

- **요소 짝짓기.** 역할 + 접근 이름 + 자기 글자 + 같은 이름의 몇 번째인가로 짝짓는다. 클래스 이름이 바뀌어도 짝이 유지된다.
- **자리 이동은 따로 본다.** 간격을 좁히면 아래 요소가 모두 위로 올라간다. 범위 밖 요소는 위치(x·y)를 빼고 크기·색·글자·테두리·그림자·반경·여백·투명도만 비교한다. `scope.allowGeometry`가 거짓이면 범위 안 요소의 크기 변화도 회귀로 센다.
- **요소 단위 캡처 비교.** 페이지 전체 캡처를 그대로 빼면 자리 이동이 전부 차이로 잡힌다. 짝지은 요소마다 앞뒤 요소 캡처(`locator.screenshot`)를 떠서 비교한다. 픽셀 비교 라이브러리(`pixelmatch` 등)를 `playwright`처럼 `--no-save`로 받는다.
- **순수 함수**(같은 `fidelity.ts`): `matchElements({ before, after })`, `styleDiff({ before, after, scope, properties })`, `regressions({ before, after, touched })`, `changedArea({ diffs, scope })`.

## 6. 원인 가설과 스킬에서 고칠 지점

증거는 2절의 판정 근거와 기존 연구 기록이다. 대화 기록이 없어서 "모델이 무엇을 읽고 무엇을 확인했는가"는 직접 볼 수 없었다. 근거가 없는 것은 가설로 적었다.

| 가설 | 증거 | 강도 | 고칠 지점(설계만) |
|---|---|---|---|
| 1. 요청을 낱개 요구로 풀지 않는다 | 유형 A·D 11실행. `SKILL.md` 절차 1단계("요청을 목록으로 적는다")가 이미 있는데 시간표 "내 예약 표시"가 빠졌다(`2026-11-10-depth.md` 10절 — "요청 누락은 SKILL.md가 이미 막는 것인데 지켜지지 않았다"). 목록을 실제로 적었는지는 대화 기록이 없어 모른다 | 중간 | 절차 1단계를 "요구 표"로 — 낱개 요구마다 요청문의 값(px·hex·문구·시간)을 그대로 옮겨 적는다. 10단계 보고에 그 표를 지킴·어김·확인 못 함으로 싣는다 |

| 6. 요청한 상태로 가는 길을 만들지 않는다 | 로그인 0.6 1번째 "오류 상태를 볼 방법이 없다", 0.14도 판정이 오류 상태를 찾지 못함(`docs/worklog/2026-10-14-readme-comparison.md`). `SKILL.md`는 "보여 달라"는 요청에만 상태 화면·주소 매개변수를 권한다 | 중간 | "요청 범위와 사실 정보" 첫 줄: 요청한 상태는 "보여 달라"가 없어도 주소 매개변수로 열리게 하고, 보고에 그 주소를 적는다 |

### 훅 안내와 우선순위의 엇갈림(가설 2 보강, 코드에서 확인)

- 편집 후 검사 훅의 warn 안내(`skills/suta/scripts/hookCore.ts`의 `WARN_GUIDE`)는 이렇다. "[사용 문제]는 기존 디자인 체계에서도 고친다. 나머지는 취향·관례라 디자인 기준이 없는 화면에서만 고치고, 프로젝트 디자인 체계의 값이면 그대로 둔다."
- 여기에는 "사용자가 명시한 값이면 그대로 둔다"가 없다. 벤치마크처럼 빈 폴더에서 만드는 화면은 "디자인 기준이 없는 화면"이다. 그래서 요청대로 이모지(`emoji-icon`)·옅은 색 면(`tinted-surface`)·여러 색(`hue-count`)을 넣으면 훅이 고치라는 쪽으로 읽힌다.
- 사용 문제는 더 엇갈린다. `SKILL.md` 우선순위 3은 "명시한 요구가 사용 문제를 만들면 요구를 따르고, 문제와 대안을 보고에 적는다"이다. 훅은 11px대 글자(`tiny-text` warn)를 "기존 체계에서도 고친다"로 안내한다. 11px 미만은 error라 편집을 막는다. 사용자가 10px를 명시하면 무시 주석 없이는 따를 수 없다.
- 이번 요청문의 `plant-care` P06(11px)과 부딪치는 요구 11개가 이 엇갈림을 직접 잰다.
- 고칠 지점(설계만): `WARN_GUIDE`와 `SKILL.md`의 "사용 문제와 취향" 아래에 "사용자가 값으로 명시한 것은 취향 warn이면 그대로 두고, 사용 문제면 따르되 보고한다. 무시 주석의 이유에 '사용자 요청'을 적는다"를 같은 말로 넣는다.

### 7.2 이번 설계의 어림

- 요청이 820~1,100자로 길고 요구가 18~20개라 생성 코드가 늘어난다. 첫 요청은 깊이 본측정의 1.3~1.6배로 어림했다. suta 앱 약 3.0달러, suta 웹 약 3.6달러, suta 없이 약 1.4달러다.
- 수정 요청은 이어진 세션이라 앞 대화가 캐시로 읽힌다. 고칠 곳이 작다. suta 0.3~0.8달러, suta 없이 0.2~0.5달러로 어림했다.

| 단계 | 실행 수 | 어림 비용 |
|---|---|---|
| 첫 요청 — 요청 6 × 조건 2(suta 없이·suta) × 반복 3 | 36 | 약 84달러(68~104) |
| 수정 요청 — 첫 요청마다 2번 | 72 | 약 33달러(18~47) |
| 판정 필요 요구 — 실행마다 짧은 판정 한 번(`I06`, 약한 넷) | 36~108 | 약 5달러(기록이 없어 불확실) |
| **합계** | 첫 요청 36 + 수정 72 | **약 120달러(90~155)** |

- 반복을 2로 줄이면 첫 요청 24 + 수정 48번, 약 80달러다. 판정 모델끼리도 갈리던 지금까지의 경험으로는 3번을 권한다.
- 선택 실험(4.3절 data 속성판)을 suta 조건에만 3번 더하면 18번, 약 60달러가 늘어난다.
- `run.mjs`의 실행당 한도(`--budget`, 기본 4달러)는 suta 웹 첫 요청에 빠듯하다. 8달러로 올려 돌린다. 한도에 걸려 끊긴 실행은 충족률이 낮게 나오므로 따로 표시한다.
- 시간은 동시 4개로 첫 요청 약 45분, 수정 요청 약 35분으로 어림한다(지난 suta 실행 중앙값 200~350초).

## 8. 확인하지 못한 것

- 지난 실행의 생성물(`index.html`·캡처·대화 기록)이 없어, 요구를 화면에서 직접 대조하지 못했다. 2절은 판정 이유에 기댄 것이라 판정이 언급하지 않은 어김은 빠졌다. 지킴은 많게, 어김은 적게 세어졌을 수 있다.
- 실행별 도구 사용(브라우저를 열었는지, 어떤 문서를 읽었는지)은 결과 JSON에 패턴 목록만 남아 가설 1·4를 직접 확인하지 못했다.
- 요구 목록의 확인 방법은 아직 어떤 생성물에도 돌려 보지 않았다. 찾기 규칙(4.3절)이 실제로 얼마나 찾는지 모른다.
- 수정 요청에 쓸 CLI 옵션(`--resume`)과 세션 보존 방식은 이번에 실행해 보지 않았다.
- 비용은 지난 짧은 요청의 비용에서 늘려 잡은 어림이다. 첫 회차 몇 번을 돌려 보고 다시 잡는다.
- 말투(`copyTone`) 판정 규칙은 문장 끝맺음만 본다. 명사로 끝나는 짧은 문구(버튼·라벨)를 어떻게 셀지는 정하지 않았다.
