# 실사용 점검 4 — 걷기 리워드 앱(게이미피케이션)

| 항목 | 내용 |
|------|------|
| 날짜 | 2026-10-12 |
| 계기 | 사용자 요청 — "간단한 게이미피케이션 앱을 구현해서 벤치마크 및 개선해보자". 주제는 걷기 리워드, 모바일 웹앱(390) 기준, 화면 6개 + 하단 탭, 일반 2번·suta 2번(개선 뒤 suta 2번 더). 화면 비교 요청으로 배포판 0.11.0을 2번 더 돌렸다(7절) |
| 반영 | 새 패턴 `celebration`(축하 오버레이), `count-up`(낭독은 최종값만), `layout-principles`(보상 색 토큰 금·은·동, tone.md 보상 색 예외, 화면 관례 "게이미피케이션·리워드" 절, 아이콘 7개), `layout-audit`(`hue-count`가 보상 색 변수를 따로 센다), `SKILL.md`, 평가, 버전 0.11.0 |

걷기 리워드 앱에서 축하·숫자 변화·보상 그림을 비교했다. 모션과 동작 줄이기 규칙이 적용되는지, 색을 줄이는 규칙 때문에 보상 표현도 사라지는지 확인했다.

## 1. 방법

이커머스·증권 점검과 같은 방식이다.

- **프로젝트**: `npm create vite`(React + TypeScript) 직후의 빈 프로젝트.
- **요청문**

  ```text
  걷기 리워드 앱을 구현해줘. 걸으면 포인트가 쌓이는 게이미피케이션 앱이야.
  홈(오늘 걸음 수·포인트 받기) / 출석·미션 / 목표 달성 축하 / 걸음 순위 / 배지 / 마이(포인트 내역·주간 기록) / 하단 탭이 있어야 해.

  - 이 프로젝트(Vite + React + TypeScript)에 만든다. 화면 사이 이동이 실제로 되게 해 줘.
  - 모바일 웹앱이 기준이고, 데스크톱 폭에서도 깨지지 않게 해 줘.
  - 걸음 센서·API는 아직 없으니 걸음·포인트·순위는 지어낸 목 데이터로 채운다. 실제 회사·브랜드 이름은 쓰지 않는다.
  - 끝나면 npm run build가 통과해야 한다.
  ```

- **실행**: `claude -p`(CLI 기본 모델)다. 편집은 자동 승인하고 Bash를 허용했다. 조건 사이에 다른 것은 플러그인(`--plugin-dir`) 하나뿐이다. 초기화 기록으로 suta가 실린 것을 확인했다.
- **측정**: 빌드한 앱을 `vite preview`로 띄워 화면 6개를 쟀다.
  - 캡처: 390×844(기준, 기기 배율 2, 터치), 1440×900, 320(가로 넘침).
  - 검사: axe-core(WCAG A·AA, 390과 1440), suta 통합 검사, 렌더 지표(상자 안 상자·12px 미만 글자 등).
  - 게이미피케이션 지표: UI 색 계열, 그라데이션, 화면의 이모지 수, 큰 숫자의 쉼표와 `tabular-nums`, 진행 표시의 값 낭독.
  - 모션: 화면마다 들어온 직후와 2.5초 뒤에 도는 애니메이션(`document.getAnimations()`)을 셌다. 무한 반복, 레이아웃 속성, 동작 줄이기(`reducedMotion: 'reduce'`)에서도 움직이는 것을 따로 셌다.
  - 보상 흐름: 홈에서 받기·체험 걷기 버튼을 눌러 축하까지 갔다. 그동안 낭독 영역(`aria-live`·`role=status`)에 들어간 글자, 축하에서의 포커스·이름·Esc를 기록했다. 아래 표의 갱신 수는 DOM 변경 기록이며, 실제 스크린 리더의 발화 횟수를 측정한 값은 아니다.
- **블라인드 판정**: 화면마다 일반과 suta를 짝지어(1↔1, 2↔2) 이름 없이 보여 주고 고르게 했다. 짝마다 순서를 바꿔 두 번, 판정 모델 둘(기본 모델과 다른 모델)이다.
  - 준 이미지는 390 첫 화면, 390 전체(2400px까지, 화면에 고정된 요소는 감춤), 1440 첫 화면이다.
  - 기준 문장은 퍼블리싱 벤치마크와 같고("숙련된 프로덕트 디자이너가 그대로 내보낼 쪽"), 이번에는 "이 앱다운 즐거움과 동기 부여"를 더했다. suta가 화면을 밋밋하게 만드는지 보려는 것이다. suta 규칙은 넣지 않았다.

### 진행 중 바로잡은 것

- **판정용 전체 캡처의 하단 탭.** 처음에는 390 전체 캡처만 줬다. 화면에 고정된 하단 탭이 전체 캡처에서 페이지 중간에 찍혀, 판정 모델이 "하단 탭이 떠서 레이아웃이 깨졌다"며 고정 탭을 쓴 쪽(suta)을 낮게 평가했다. 첫 화면 캡처(고정 요소 포함)와 전체 캡처(고정 요소 감춤)를 함께 주게 고치고 다시 판정했다. 고치기 전 1차 판정은 12:12, 고친 뒤 17:7이다. 아래 숫자는 모두 고친 뒤의 것이다.
- **해시 주소 앱의 상태.** 해시만 바뀌면 페이지를 새로 고치지 않아 앞 화면의 상태(받은 포인트)가 다음 화면으로 넘어갔다. 화면마다 빈 페이지를 거쳐 새로 열게 했다.
- **축하까지 가는 길.** 실행마다 축하로 가는 길이 달랐다(걸음이 목표를 넘으면 자동 이동, 마지막 보상 받기, 보너스 받기, "축하 보기" 버튼). 받기 → 축하 버튼 → 체험 걷기 → 기다리기 순으로 시도하고, 다른 화면으로 가 버리는 버튼은 다시 누르지 않게 했다.

## 2. 1차 결과 — suta 0.10

화면 6개 합계다.

| | 일반 1 | 일반 2 | suta 0.10 1 | suta 0.10 2 |
|---|---|---|---|---|
| 시간·비용 | 2.2분 · 0.34달러 | 2.1분 · 0.30 | 8.0분 · 1.49 | 5.3분 · 1.05 |
| axe 위반(390) | 51(색 대비 38, 이름 없는 진행 막대 13) | 35(색 대비 33) | 0 | 0 |
| 화면의 이모지 | 41 | 64 | 0 | 0 |
| 12px 미만 글자 | 32 | 44 | 0 | 0 |
| `tabular-nums` 숫자 | 1/50 | 13/46 | 42/61 | 39/49 |
| 쉬는 축하 화면의 무한 반복 애니메이션 | 25(떨어지는 색종이 24 + 튀는 트로피) | 28 | 0 | 0 |
| 동작 줄이기에서 움직이는 것 | 0 | 0 | 0 | 0 |
| 축하 형태 | 별도 페이지 + 이모지 트로피 + 색종이 | 같음 | 별도 페이지 + 체크 표시 | 별도 페이지 + 체크 링 |
| 축하까지 낭독 영역 갱신 수 | 2 | 0 | 6 | 64 |
| suta 검사 | error 1 · warn 16 | error 1 · warn 21 | 0 · 2 | 0 · 4 |

- **두 조건 모두 한 것**: 강조색으로 초록을 골랐다. 걸음 수 링과 하단 탭 5칸, 요일 출석 줄을 뒀다. 일반 쪽도 동작 줄이기 블록을 넣었다.
- **일반 쪽**: 탭·배지·메달·불꽃을 모두 이모지로 그렸다(소스에 23·32자). 축하는 이모지 트로피가 계속 튀고 색종이가 무한히 떨어지는 별도 페이지다. 진행 막대의 폭(`width`)을 움직여 suta 검사의 error가 났다.
- **suta 0.10 쪽이 놓친 것**
  - 축하를 별도 페이지로 옮겨 체크 표시와 통계 목록을 늘어놓았다. 축하 연출이 없다.
  - 순위 1~3위를 다른 행과 똑같이 뒀다.
  - 배지는 같은 모양 선 아이콘을 회색 상자에 넣어, 얻은 것이 그림으로 드러나지 않았다.
  - 한 실행은 매초 바뀌는 "목표까지 N걸음"과 카운트업 숫자를 낭독 영역(`role=status`)에 넣었다. 축하까지 낭독 영역이 64번 갱신됐다(+0P, +5P, +11P…). `count-up` 패턴의 React 래퍼가 중간값을 숨기지 않았고, 문서의 안내는 한 줄뿐이었다.
- **1차 블라인드 판정**

  | 판정 모델 | suta : 일반 | 홈 | 출석·미션 | 축하 | 순위 | 배지 | 마이 |
  |---|---|---|---|---|---|---|---|
  | 기본 모델(화면을 만든 모델과 같다) | 17 : 7 | 4:0 | 4:0 | 1:3 | 1:3 | 3:1 | 4:0 |
  | 다른 모델 | 19 : 5 | 4:0 | 4:0 | 2:2 | 2:2 | 3:1 | 4:0 |

  기본 판정 모델은 축하와 순위에서 일반 조건을 더 많이 선택했다. 이유는 "체크 아이콘과 흰 배경만 있어 축하 느낌이 약하다", "시상대·메달이 없는 밋밋한 목록"이었다. 일반 조건의 이모지 탭 아이콘에는 "조잡하다"는 평가가 반복됐다.

## 3. 레퍼런스

지난번과 같은 디자인 레퍼런스 사이트의 공개 앱 화면이다(로그인 없이 보이는 화면). 서비스 이름은 실험 폴더에만 둔다. 게이미피케이션 앱의 화면 대부분은 로그인 뒤라 웹 레퍼런스는 따로 모으지 않았다.

| 서비스 | 본 화면 | 관찰 |
|---|---|---|
| 영단어 학습 앱 | 584장 | 홈 1순위는 캐릭터 + 진행 링(%) + 주 버튼 "오늘의 학습". 머리 오른쪽에 재화 숫자 2개. 출석 요일 줄 7칸(오늘 채움 + 체크), 누르면 달력과 연속·총 출석일 |

- **공통**: UI는 강조색 하나다. 메달·트로피·코인 같은 보상 그림만 따로 칠한다. 축하는 별도 페이지가 아니라 지금 화면 위에 띄우고, 버튼은 하나다. 무한 반복 애니메이션은 쉬는 화면에 없다.
- **한계**: 서비스 셋, 각자 한 서비스의 사례라 "관례"로는 약한 근거다. 커피 앱(별 적립·등급) 858장은 받았지만 이번에 분석하지 않았다.

## 4. 반영 — suta 0.11

- **새 패턴 `celebration`(축하 오버레이)**
  - 네이티브 `<dialog>.showModal()`로 지금 화면 위에 띄운다. 큰 보상 그림 하나(보상 색 원판 위 흰 아이콘), 한 줄 제목(대화상자 이름), 보상과 설명(대화상자 설명), 버튼 하나(열리면 포커스).
  - 조각 14개가 위와 양옆으로 한 번 퍼져 그림 둘레에 남는다. 아래로는 내려가지 않는다(제목·보상 글자를 가리지 않게). 무한 반복은 없다.
  - 동작 줄이기면 조각은 날지 않고 제자리에 놓이고, 그림·패널은 짧은 페이드만 한다.
  - 코어(`burstPieces`, seed로 궤적 고정)·React 래퍼·CSS, 테스트 10개(TDD), 데모(국수집 도장 카드).
  - 처음에는 작은 보상용 자동 닫힘(`autoCloseMs`)도 넣었다. 실제 브라우저에서 확인하니 모달의 어두운 막이 화면 전체라 포인터가 늘 안에 있는 것으로 잡히고, 열리면 포커스도 안으로 들어가 타이머가 멈춘 채 닫히지 않았다. jsdom 테스트로는 잡히지 않았다. 자동 닫힘을 빼고, 자주 생기는 작은 적립은 토스트(`toast-stack`)로 알리게 했다. 금융 앱 레퍼런스도 그렇다.
  - 데모에서는 여는 버튼을 비활성으로 바꾸면 닫은 뒤 포커스가 문서 처음으로 가 버리는 것을 확인했다. "여는 버튼을 닫힌 뒤에도 남겨 둔다"를 주의사항에 적었다.
- **`count-up`**(TDD, 테스트 2개): React 래퍼가 굴러가는 숫자를 `aria-hidden`으로 두고, 최종값을 숨긴 글자(`.count-up-sr`)로 따로 넣는다. 낭독 영역에 중간값 대신 최종값을 노출한다.
- **보상 색 토큰**(TDD): `--color-reward`(금 `#b07d00`)·`--color-reward-silver`(은 `#7b8088`)·`--color-reward-bronze`(동 `#a8662b`). 그림이라 흰 면·옅은 바탕에서 3:1 이상이다. 금색 면 위 글자는 주 글자색이어야 4.5:1이다.
- **`tone.md` 2절 "예외 — 보상 그림의 색(금·은·동)"**: 그림에만 쓴다. 글자·버튼·면에는 쓰지 않는다. 얻은 배지는 보상 색, 못 얻은 배지는 회색 + 자물쇠. 이모지 메달을 쓰지 않는다.
- **`hue-count`**(TDD, 테스트 2개): 이름에 reward·medal·coin·gold·silver·bronze가 든 변수의 색은 계열 수에서 뺀다. 직접 쓴 금색은 그대로 센다.
- **화면 관례 "게이미피케이션·리워드" 절**: 색, 홈, 혜택 목록, 미션 목록, 축하, 순위, 배지, 출석·연속 기록, 마이·포인트 내역, 숫자 맞추기, 낭독, 하지 말 것.
- **아이콘 7개**(Lucide): `trophy`·`medal`·`lock`·`flame`·`calendar-check`·`footprints`·`chart`. 45개 → 52개.
- **`SKILL.md`**: 화면 유형에 게이미피케이션, 4단계에 보상 색, 6단계 예시, 금지선 4행(축하·순위, 보상 그림, 축하 모션, 낭독 영역), 값 표 2행(보상 색, 축하 시간), 체크리스트 1항목.
- **평가**: 트리거 2개, `celebration` 선택 평가(9개). 472/472.

## 6. 2차 뒤 고친 것 (3차에서 확인)

- **축하 그림**: 보상 색 원판 위 흰 아이콘으로 바꿨다. 선 아이콘만 두면 확인 창처럼 보인다. 조각은 끝난 뒤에도 그림 둘레에 남고(위와 양옆만), 어두운 막을 48%에서 60%로 올렸다. 브라우저로 조각이 한 번 날아와 멈추는 것, 동작 줄이기에서는 제자리에 놓이는 것, 포커스가 버튼으로 갔다가 닫으면 여는 버튼으로 돌아오는 것을 확인했다.
- **화면 관례**
  - 홈의 주 버튼은 늘 그 자리에 둔다. 받을 것이 없으면 비활성 + 남은 조건을 버튼 글자로. 링 → 주 버튼 → 오늘 요약 → 출석 줄 → 미션 2~3개로 첫 화면 아래를 채운다.
  - 혜택 목록(진행 없음)과 미션 목록(진행 있음)을 나눴다. 미션 행은 이름이 보상보다 크고, 막대는 모든 행이 같은 길이, 받을 수 있으면 작은 버튼이다.
  - 출석 칸 아래에 그날 보상을 쓰고 마지막 날 큰 보상을 굵게 둔다.
  - 주간 기록은 지난 7일(오늘이 오른쪽 끝)로 그린다.
  - 연속 출석일과 체크 칸, 목표를 넘긴 뒤의 문구, 축하와 홈의 걸음 수가 서로 맞게 한다.
- **출석 축하**: 하루 한 번인 출석은 축하 오버레이로 띄워도 된다(학습 앱·공동구매 앱). 토스트는 자주 생기는 작은 적립에만 쓴다. 2차 스냅숏은 출석까지 토스트로 묶은 문구였다.
