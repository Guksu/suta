## 1. 개요

여섯 번째 묶음(PR #63) 뒤에 고친 것은 네 가지다. 데스크톱 작성 폼 배치, 세그먼트 기본값, 예약 폼 금액, 반려동물 아바타다. 이것을 업종이 다른 새 요청 3개로 두 조건 3번씩, 모두 18번 돌렸다. 기준은 측정 보강(#64)과 glass-nav 고침(#65)까지 들어간 main(`19699b0`)의 스냅숏이다.

## 2. 작업내용

- 실행·측정 18번, 캡처 18개를 눈으로 확인했다. 이어 두 모델로 블라인드 판정을 돌렸다. 생성 비용은 20.47달러다.
- **측정 스크립트의 결함 두 가지.**
  - 하단 고정 바가 잘려 나감: 캡처는 아래쪽 고정 바를 문서 끝으로 옮긴 뒤 2,400px에서 자른다. 그래서 긴 페이지에서는 바가 잘려 나갔다.
    - 숙소 등록 6개 중 5개(suta 없이 3, suta 2)가 그랬다. 지난 실행 7회분(126개 페이지)에는 없었다.
    - 고침: 하단 고정 바를 찍히는 영역의 끝에 둔다(`CAPTURE_MAX`).
  - 넓은 바가 위로 밀려 찍힘(PR #66 리뷰가 찾음): 화면보다 넓은 바를 `absolute`로 바꾸면 문서가 옆으로 넘쳐 `innerHeight`가 늘어난다(844 → 888). 늘어난 값으로 자리를 셈해 바가 그만큼 위에 찍혔다.
    - suta 숙소 등록 1번째는 44px 위로 밀려 마지막 "공개" 항목을 가렸다. 다섯 번째 묶음의 강의 등록 suta 없이 3번째도 143px 밀렸다(그 판정은 다시 하지 않았다).
    - 고침: 화면 크기를 스타일을 바꾸기 전에 한 번 읽는다.
  - 처음에 의심한 다른 원인(조상이 sticky·relative일 때 옮긴 바가 엉뚱한 자리에 찍힘)은 144개 페이지에서 한 번도 없어 고치지 않았다.
  - 숙소 등록 6개를 두 고침 뒤 다시 재고 두 모델로 다시 판정했다. 결과 파일은 둘이다. `gap7-web-results.json`은 고치기 전이고 `captureNote`로 표시했다. `-v2`는 두 고침 뒤의 정식 결과다. 앱 12개는 두 결함 모두 없어 그대로 뒀다.
  - suta 1번째의 하단 바 문구가 화면 양끝에 붙은 것은 생성된 페이지의 실수다. 바에 카드용 클래스를 함께 달아 모바일의 음수 좌우 여백이 걸렸다.
- 판정(suta : 없이):

  | 요청 | 기본 모델 | 다른 모델 |
  |---|---|---|
  | 진료 예약 | 4 : 2 | 3 : 3 |
  | 세차 예약 | 5 : 1 | 6 : 0 |
  | 숙소 등록 | 6 : 0 | 2 : 4 |
  | 합계 | 15 : 3 | 11 : 7 |

  - 기본 모델(생성 모델과 같다)은 여섯 번째 묶음에 이어 세 요청 모두 suta를 골랐다.
  - 숙소 등록은 세 번 판정했다. 고치기 전 4 : 2·4 : 2, 첫 고침 뒤 5 : 1·3 : 3, 두 고침 뒤 6 : 0·2 : 4다. 다른 모델은 거의 같은 캡처에서 흔들렸다.
  - 순서를 바꿔도 같은 쪽을 고른 쌍은 두 모델 모두 9쌍 중 8쌍이다(기본 7 : 1, 다른 모델 5 : 3).
- 지난 고침이 쓰였는가:
  - 아바타 진료 3/3, 데스크톱 묶음 숙소 3/3, 테두리 입력칸 숙소 3/3, 체크인 방식 기본값 3/3.
  - 금액 항목별 내역은 진료 3/3·세차 1/3, 하단 바의 금액은 세차 3/3·진료 0/3.
- 진 판정 10번 중 9번이 상대 쪽의 더 풍부한 구성을 들었다.
  - 요청에 없는 구역(병원 정보 배너·증상 빠른 선택 칩·미리보기 카드)은 더하지 않는다.
  - 요청한 것을 보이는 방식(수의사 프로필 카드·필수 항목 진행 표시)은 범위 안이다.
- 함께 짚은 사용 문제를 고쳤다(다시 재지 않음).
  - 반려동물 카드 높이가 서로 다름(4번): 격자 칸은 늘었지만 안쪽 테두리 상자가 157·177px였다.
  - "숙소 유형" 라벨이 버튼에 붙음(2번): 다른 칸은 8px인데 0px였다.
  - 고침: 화면 관례 작성 폼 절과 확인 목록에 "같은 줄의 고르는 칸은 모양을 맞춘다"를 더했다. 보이는 상자까지 같은 높이, 라벨과 칸 사이 간격 통일.
  - 시간 칸 폭(1번)은 관례로 만들지 않았다. suta의 시간 칸은 이미 같은 폭이었고, 판정이 말한 것은 날짜 줄과 시간 칸의 폭 차이로 보인다(PR #66 리뷰).
- 기록:
  - 연구 문서 15절과 한눈에 요약.
  - 화면 비교 문서 2벌의 맨 앞 절과 비교 이미지(각 조건의 첫 실행).
  - README 2벌의 "관례가 없던 화면" 절: 일곱 묶음, 117번 실행, 21개 요청 합계 기본 63 : 63·다른 모델 53 : 73.
  - `docs/benchmark(.en).md`의 캡처 설명.

## 3. 주의사항

- 조건마다 3번이고, 판정 모델 하나는 생성 모델과 같다.
- 다른 모델의 숙소 등록 판정은 세 번 사이에 4 : 2 → 3 : 3 → 2 : 4로 흔들렸다.
  - 첫 판정과 두 번째 사이에는 하단 바가 잘렸던 캡처 5개(양쪽)가 바뀌었다. suta 1번째의 캡처는 그대로였다(페이지 높이 2,265px로 2,400px 아래).
  - 두 번째와 세 번째 사이에는 suta 1번째의 하단 바 자리만 바뀌었다.
- 판정 프롬프트는 캡처가 "모바일 전체 화면"이라고만 말한다. 2,400px보다 긴 페이지는 잘리고 하단 바가 그 끝에 겹쳐 찍히는데, 판정 1번은 이것을 "하단 바가 공개 토글을 가린다"고 읽었다. 판정에 알리는 것은 다음 묶음부터 검토한다.
- 하단 바에 금액을 넣는 관례는 이미 있었는데 진료 예약 3번에서 따르지 않았다. 문장을 바꾸지 않았고 이유는 찾지 못했다.
- 화면 비교 이미지는 `docs/assets/`에 두었다(규칙 12).
