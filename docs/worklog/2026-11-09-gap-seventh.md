## 1. 개요

여섯 번째 묶음(PR #63) 뒤에 고친 것은 네 가지다. 데스크톱 작성 폼 배치, 세그먼트 기본값, 예약 폼 금액, 반려동물 아바타다. 이것을 업종이 다른 새 요청 3개로 두 조건 3번씩, 모두 18번 돌렸다. 기준은 측정 보강(#64)과 glass-nav 고침(#65)까지 들어간 main(`19699b0`)의 스냅숏이다.

## 2. 작업내용

- 실행·측정 18번, 캡처 18개를 눈으로 확인했다. 이어 두 모델로 블라인드 판정을 돌렸다. 생성 비용은 20.47달러다.
- **측정 스크립트의 결함.** 캡처는 아래쪽 고정 바를 문서 끝으로 옮긴 뒤 2,400px에서 자른다. 그래서 2,400px보다 긴 페이지에서는 하단 바가 잘려 나갔다.
  - 숙소 등록 6개 중 5개(suta 없이 3, suta 2)가 그랬다. 다른 모델이 suta 3번째를 "모바일에서 등록 버튼이 보이지 않는다"고 두 번 짚었다.
  - 지난 묶음 7개(126개 페이지)에는 없었다.
  - 고침: 하단 고정 바를 찍히는 영역의 끝에 둔다(`CAPTURE_MAX`). 숙소 등록 6개만 다시 재고 두 모델로 다시 판정했다. 결과는 `gap7-web-results-v2.json`이고, 고치기 전 결과도 `gap7-web-results.json`에 남겼다.
  - 같이 의심한 다른 원인(조상이 sticky일 때 옮긴 바가 엉뚱한 자리에 찍힘)은 144개 페이지에서 한 번도 없어 고치지 않았다. suta 1번째의 하단 바가 화면 끝에 붙은 것은 생성된 페이지의 실수였다. 바에 카드용 클래스를 함께 달아 모바일의 음수 좌우 여백이 걸렸다.
- 판정(suta : 없이, 숙소 등록은 고친 뒤):

  | 요청 | 기본 모델 | 다른 모델 |
  |---|---|---|
  | 진료 예약 | 4 : 2 | 3 : 3 |
  | 세차 예약 | 5 : 1 | 6 : 0 |
  | 숙소 등록 | 5 : 1(고치기 전 4 : 2) | 3 : 3(고치기 전 4 : 2) |

  - 두 모델 모두 진 요청이 없는 것은 처음이다.
  - 순서를 바꿔도 같은 쪽을 고른 쌍은 두 모델 모두 9쌍 중 7쌍이다.
- 지난 고침이 쓰였는가:
  - 아바타 진료 3/3, 데스크톱 묶음 숙소 3/3, 체크인 방식 기본값 3/3, 테두리 입력칸 2/3.
  - 금액 항목별 내역은 진료 3/3·세차 1/3, 하단 바의 금액은 세차 3/3·진료 0/3.
- 진 판정 10번 중 9번이 상대가 더한 요청에 없는 구역(병원 정보 배너·수의사 프로필·미리보기 카드·진행 표시)을 들었다. 요청 범위 규칙상 더하지 않는다.
- 함께 짚은 사용 문제를 고쳤다(다시 재지 않음).
  - 반려동물 카드 높이가 서로 다름(4번), 라벨과 버튼 사이 간격(2번), 시간 칸 폭(1번).
  - 고침: 화면 관례 작성 폼 절과 확인 목록에 "같은 줄의 고르는 칸은 모양을 맞춘다"를 더했다. 한 줄 선택 카드는 같은 높이, 시간·날짜 칸 격자는 같은 폭의 열, 라벨과 칸 사이 간격은 모든 칸에서 같게.
- 기록:
  - 연구 문서 15절과 한눈에 요약.
  - 화면 비교 문서 2벌의 맨 앞 절과 비교 이미지(각 조건의 첫 실행).
  - README 2벌의 "관례가 없던 화면" 절(일곱 묶음, 117번 실행, 21개 요청 합계 62 : 64·54 : 72).
  - `docs/benchmark(.en).md`의 캡처 설명.

## 3. 주의사항

- 조건마다 3번이고, 판정 모델 하나는 생성 모델과 같다.
- 숙소 등록의 다른 모델 판정은 캡처를 고친 뒤 4 : 2 → 3 : 3으로 나빠졌다. 고친 캡처에서 suta 1번째의 하단 바 실수와 상대의 진행 표시 바가 보이게 됐다.
- 하단 바에 금액을 넣는 관례는 이미 있었는데 진료 예약 3번에서 따르지 않았다. 문장을 바꾸지 않았고 이유는 찾지 못했다.
- 화면 비교 이미지는 `docs/assets/`에 두었다(규칙 12).
