# 측정 — 넘친 페이지에서 표 열의 화면 폭

| 항목 | 내용 |
|------|------|
| 날짜 | 2026-11-09 |
| 작성 | Claude Code |
| 관련 경로 | `scripts/benchmark/measure.mjs`(`clipProbes`), `docs/benchmark(.en).md`, `docs/research/2026-11-06-reference-gaps.md` 14절, `docs/worklog/2026-11-06-gap-sixth.md` |

## 1. 개요

여섯 번째 재측정(PR #63)에서 "측정의 빈틈"을 하나 적었다. suta 없이 미용 예약 1번째 실행에서 하단 바의 금액 문구가 화면 끝에서 잘렸는데, 측정은 "칸 밖으로 잘린 글자"로 세지 않았다는 내용이다. 후속으로 이것을 고치려고 실제 페이지를 들여다봤다. 그런데 원인은 달랐다.

- 이 페이지는 390px에서 가로로 넘쳤다. 측정은 이것을 `overflow390`으로 이미 셌다.
- 모바일 에뮬레이션은 넘친 페이지를 휴대폰처럼 다룬다. `innerWidth`가 콘텐츠 폭(883px)까지 늘어나고, `left: 0; right: 0`인 고정 바도 883px이 된다.
- 금액 문구(218~403px)와 예약 버튼(564~628px)은 바 안에 있다. 캡처가 왼쪽 390px만 잘라 찍어서 잘린 것처럼 보였다.
- 그러니 측정의 빈틈이 아니라 넘침 한 가지였다. 기록을 바로잡았다.

들여다보다 실제 결함을 하나 찾았다. 표 열 측정이 화면 폭을 `innerWidth`로 잡는다. 그래서 표가 페이지 자체를 넘치게 하면, 늘어난 `innerWidth` 안에 열이 다 들어가 "390px 밖의 열 0"으로 셌다.

## 2. 작업내용

- `measure.mjs`의 `clipProbes`: 화면 폭을 `document.documentElement.clientWidth`로 바꿨다. 이 값은 넘쳐도 390이다. 이유는 주석에 적었다.
- 재현 페이지로 확인했다. 5열 표이고, 390px에서 오른쪽 두 열의 끝이 419·520px이다.

  | 재현 페이지 | 고치기 전 | 고친 뒤 |
  |---|---|---|
  | 표가 페이지 자체를 넘침(`innerWidth` 521) | 0 | 2 |
  | 같은 표를 가로 스크롤 칸 안에 둠 | 2 | 2 |
  | suta 없이 미용 예약 1번째(넘침, 고정 바) | 표 없음 — `overflow390` 참, 잘린 글자 0 | 같음 |

- 지난 실행 전체(`suta-gap`~`suta-gap7`)에서 표가 있는 페이지 31개를 옛 기준과 새 기준으로 다시 셌다. 숫자가 바뀌는 페이지는 없었다. 넘친 페이지 5개는 모두 표가 스크롤 칸이나 잘라내는 칸 안에 있었다. 그래서 지난 결과 JSON과 문서의 숫자는 그대로다.
- 기록 정정:
  - 연구 문서 14절과 여섯 번째 재측정 작업 기록의 "측정의 빈틈"을 원인(가로 넘침과 캡처 자르기)으로 고쳤다.
  - `docs/benchmark(.en).md`의 표 열 지표 설명에 화면 폭 기준을 더했다.

## 3. 주의사항

- 브라우저 안에서 도는 코드라 단위 테스트가 없다. 순수 판정 로직(`scripts/lib/clipCheck.ts`)은 바뀌지 않았다. 확인은 재현 페이지 3개와 지난 실행 31개로 했다.
- 같은 파일의 다른 `innerWidth` 두 곳은 그대로 뒀다. 하나는 면 넓이를 셀 때의 상한, 다른 하나는 캡처 전에 화면 밖 고정 요소를 숨기는 판정이다. 넘친 페이지에서 조금 넓게 보지만, 지표 숫자를 바꾸는 판정이 아니다.
- 넘친 페이지의 390 캡처는 왼쪽 390px만 보인다. 실제 휴대폰은 페이지를 축소해 보일 수 있다. 판정은 잘린 캡처를 보고 "버튼이 보이지 않는다"고 했는데, 넘침이라는 같은 결함을 본 것이라 캡처 방식은 바꾸지 않았다.
- 화면 결과가 없는 측정 변경이라 화면 비교 이미지는 만들지 않았다(규칙 12).
