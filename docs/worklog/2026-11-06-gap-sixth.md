## 1. 개요

다섯 번째 묶음 뒤에 고친 것이 있었다. 가로 줄의 첫 항목 정렬, 데스크톱 작성 폼, 기사 표현, 요청 범위의 경계와 사이트 메뉴 이름(PR #59·#60)이다. 이 고침들은 아직 다시 재지 않았다. 그래서 업종이 다른 새 요청 3개로 두 조건을 3번씩, 모두 18번 돌렸다. 기준은 `segmented-control` 고침(PR #62)까지 들어간 main(`147413e`)의 스냅숏이다. 요청문은 `evals/benchmark/gap6-app-prompts.json`·`gap6-web-prompts.json`에 있다.

## 2. 작업내용

- 실행과 측정 18번, 캡처 18개를 눈으로 확인했다(결함 없음). 이어 두 모델로 블라인드 판정 36번을 돌렸다. 생성 비용은 20.47달러다(실행별 `costUsd` 합).
- 판정(suta : 없이, 기본 모델·다른 모델):

  | 요청 | 기본 모델 | 다른 모델 |
  |---|---|---|
  | 미용 예약 | 4 : 2 | 3 : 3 |
  | 채용 공고 | 5 : 1 | 2 : 4 |
  | 집 소개 기사 | 6 : 0 | 4 : 2 |

  기본 모델(생성 모델과 같다)이 처음으로 세 요청 모두 suta를 골랐다(15 : 3). 다른 모델은 9 : 9였다. 순서를 바꿔도 같은 쪽을 고른 쌍은 기본 모델 8쌍(suta 7, 없이 1), 다른 모델 6쌍(3 : 3)이다.
- 확인된 고침:
  - 기사 관례: 드롭캡·번호 소제목·가운데 제목 묶음, 메뉴 4~5개와 모바일 메뉴 버튼. 여행 기사 0 : 6, 0 : 6에서 이번 6 : 0, 4 : 2가 됐다. 이긴 판정은 메뉴(7번)와 번호 소제목(4번)을 들었고, 드롭캡을 든 판정은 없었다.
  - 가로 줄 정렬: suta 3번 모두 날짜 줄의 첫 칸이 본문 정렬선에 있었다.
  - 세그먼트: 채용 공고 2·3번째 실행이 정본 세그먼트를 복사했다. 정본이 이제 `transform`만 움직이므로 레이아웃 속성을 움직인 화면은 0/3이다. 1번째 실행은 thumb 없는 세그먼트를 직접 짰다.
- 진 이유와 고침(다시 재지 않음):
  - 데스크톱 작성 폼의 배치. 진 판정 5번 모두가 짚었다. 입력 열과 패널 사이가 크게 비었거나, 머리보다 좁은 본문이 왼쪽에 붙었다.
    - 고침: 입력 열과 패널을 24~32 간격의 한 묶음으로 두고, 사이트 머리·페이지 제목과 좌우 끝을 맞춘다(화면 관례·확인 목록).
  - 아무것도 고르지 않은 세그먼트가 비활성처럼 보였다(판정 1번 — 근거가 약하다).
    - 고침: 세그먼트는 한 칸이 늘 골라져 있다. 기본값이 없는 필수 선택은 테두리 칩이나 라디오다(화면 관례·확인 목록·`segmented-control` 주의사항). 주의사항의 "제출형 폼이면 라디오"는 작성 폼 관례와 맞게 고쳤다.
  - 회색 바탕·흰 패널·회색 채움 칸이 겹쳐 칸이 흐렸다(판정 2번).
    - 고침: 그 경우에는 1px 테두리 칸을 쓴다(화면 관례·확인 목록).
  - 미용 예약의 금액 구역이 세 번 모두 안내 문장 한 줄뿐이었다(1·2번째는 상대의 결함 덕에 이겼다). 진 판정 5번 모두 상대의 금액이 든 하단 고정 바를 들었고, 4번은 항목별 금액 내역도 들었다.
    - 고침: 금액이 있는 예약·신청 폼은 항목별 내역(추가 요금 줄은 데이터에 있을 때만) + 금액이 든 하단 고정 바를 둔다. 요청한 내용을 보이는 방식이라 요청 범위 안이다. 가게 정보·소요 시간처럼 요청에 없는 구역·데이터는 더하지 않고 제안한다(화면 관례·확인 목록).
  - 반려견 아바타로 쓴 `art--pet`이 "곰 모양"으로 읽혔다.
    - 고침: 종이 정해진 자리나 작은 원형 아바타에는 이름 첫 글자 원을 둔다(화면 관례).
- 기록:
  - 연구 문서 14절과 한눈에 요약.
  - 화면 비교 문서 2벌의 맨 앞 절과 비교 이미지(각 조건의 첫 실행).
  - README 2벌의 "관례가 없던 화면" 절(여섯 묶음, 99번 실행, 판정 합계).
- PR #63 리뷰 반영: 위 문장들의 과장과 숫자(비용 합계, 정본 세그먼트를 복사한 실행 수, 메뉴 수, 판정 수, 인용)를 원자료에 맞췄다. 데스크톱 묶음 폭이 사이트 콘텐츠 폭(1120~1280)과 부딪히지 않게 "머리와 좌우 끝을 맞춘다"로 고쳤다.

## 3. 주의사항

- 조건마다 3번이고, 판정 모델 하나는 생성 모델과 같다. 그 기본 모델이 15 : 3, 다른 모델이 9 : 9다. 다른 모델의 순서가 뒤집힌 3쌍은 두 번 모두 나중에 보여 준 쪽을 골랐다.
- suta 없이 미용 예약 1번째의 하단 바 금액이 잘려 보인 것은 페이지의 가로 넘침 때문이다. 측정은 `overflow390`으로 셌다. 처음에 적은 "측정의 빈틈"은 잘못 짚은 것이라 고쳤다(`2026-11-09-measure-screen-width.md`).
- 채용 공고는 판정 모델에 따라 결과가 반대였다. 다른 모델은 상대의 파란 주 버튼과 테두리 입력칸을 "위계가 분명하다"고 두 번 골랐다. 강조색은 suta의 색 기준이라 바꾸지 않았다.
- 기사에서 진 2번은 상대의 종이색 바탕과 명조 부제를 골랐다. 취향 쪽이라 고치지 않았다.
- 화면 비교 이미지는 벤치마크 결과라 `docs/assets/`에 두었다(규칙 12). 관례 고침은 문서만 바꿔 데모 화면은 그대로다.
